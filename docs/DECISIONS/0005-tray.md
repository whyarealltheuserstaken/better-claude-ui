# 0005 — System tray / menu bar

Status: accepted (2026-11-26)

## Decision
An optional tray icon, off by default (Settings > Usage widget). It shows the readings you choose and tells you when Claude is waiting. Code: `src-tauri/src/tray.rs`, `src/lib/widget/tray.ts`, `src/lib/trayBridge.ts`, `components/TrayPanel.svelte`, `routes/tray/`.

- **Windows and macOS:** a left click opens a small borderless window; a right click shows a native menu (Open, Quit). **Linux** reports no tray clicks, so its menu also lists the readings as text.
- **Why a panel at all:** Apple's guidance prefers a menu for menu bar extras unless the content is too complex. Bars and rings are the reason.
- **The main window stays the only brain.** It works out every reading and sends the panel a finished view over events; Rust only draws the icon, tooltip and menu from what the window reports. No second copy of the usage logic exists.

## Safety
- **Nothing can be approved from the tray.** The panel has no approve control, and Rust rejects every app command from any window except `main`. This is needed because Tauri lets every window call an app's own commands by default. `capabilities/tray.json` limits the panel to listening, emitting and hiding itself.
- Messages are checked on arrival (`parseTrayAction`, `parseTrayView`). The panel can change which readings it shows and their size, never whether the tray is on or whether the app keeps running.
- Open and Quit travel through the main window. The native right-click menu works even if that window hangs.
- **The window can never become unreachable.** Closing hides it only if the tray icon exists and **Keep running** is on. Turning the tray off shows the window. If the icon cannot be created, the app says so and closing quits.
- A hidden panel is still a window and would keep the process alive, so it is destroyed when the main window really closes.
- **Only one copy runs** (`tauri-plugin-single-instance`). With the window hidden, people start the app again from the Start menu; a second copy would add a second icon and the two would overwrite each other's settings and history. A second launch now shows the running window and exits. This applies with the tray off too. A debug build and an installed release share the app id, so one blocks the other.
- Quit from the tray asks first while Claude is replying or waiting.
- Restoring a backup never turns the tray or **Keep running** on.

## Notes
- The panel is created on its own thread: creating a window inside an event handler deadlocks WebView2.
- Clicking the icon while the panel is open first takes focus away from the panel, which hides it. A click within 300 ms of that is treated as "close", not "open again".
- The panel is solid rather than glass: it is a separate window with nothing of the app behind it.
- The icons are drawn by `tools/make-tray-icons.mjs`. Waiting differs in shape (a disc with an exclamation mark), not only in colour. The icon never draws a live percentage.
- Debug builds only: `BCU_OPEN_TRAY_PANEL` opens the panel when the icon is created, because a test cannot click a tray icon.

## Verified, and not
Verified on Windows in the real app (`node tools/e2e.mjs tray`): the panel receives its view and cannot call app commands; closing with Keep running hides the window; a permission request made while hidden reaches the tray status and the panel; Quit while waiting asks first and dismissing it keeps the app running; Open brings the window back; with Keep running off, closing quits even with a hidden panel; starting the app again while hidden leaves one copy and shows its window.

**Not verified:** clicking the real icon (left or right), where the panel appears, hiding when it loses focus, how the icon looks on the taskbar, and anything on macOS or Linux. On Linux the tray library loads `libappindicator` when the tray is first turned on; on a system without it the app may crash rather than report an error.
