# 0003 — In-app updater

Status: accepted (2026-11-26)

## Decision
Use `tauri-plugin-updater` and drive it **from Rust**, not from the webview.

- **Where it runs.** `check_for_update`, `download_update` and `install_update` are Tauri commands in `commands.rs`; pure helpers (error wording, HTTPS rule, release-note trimming) are in `updates.rs`. The webview never calls the plugin's own commands: `updater:default` is deliberately **not** in `capabilities/default.json`, and the update flow needs no network access from the webview, so the CSP (ADR 0002) is unchanged.
- **Trust.** Updates are verified against the **minisign public key** in `tauri.conf.json` (`plugins.updater.pubkey`). `download()` verifies the signature before returning bytes and `install()` verifies again, so a tampered or wrongly signed file is never installed. The plugin also rejects a manifest that announces a different version than the one that was signed. There is no setting or UI path that skips verification.
- **Transport.** The endpoint is `https://github.com/<owner>/better-claude-ui/releases/latest/download/latest.json`. Release builds refuse non-HTTPS endpoints (plugin) and non-HTTPS download URLs (`download_url_allowed`). Debug builds may use `BCU_UPDATE_ENDPOINT` to point at a local test server; that override does not exist in release builds (`#[cfg(debug_assertions)]`).
- **Flow.** Two steps so the user stays in control: *download* (progress, signature verified) then *Install and restart*. Nothing downloads or installs without a click. Automatic checks (on by default, at most once a day, can be turned off) only look and show a chip.
- **Safety around installing.** The UI blocks "Install" while any conversation is replying or a permission prompt is pending. On install, `claude` child processes are stopped first, because on Windows the updater exits the process itself (skipping the normal exit handler) and would otherwise orphan them. Saved conversations are written at the end of every turn, so nothing else is lost.
- **Config ownership.** The UI owns `auto_update_check`, `last_update_check` and `skipped_version` in `config.json`; Rust does not write the config, avoiding a save race.
- **Failure messages.** Plugin errors are mapped by type (`updates::classify`) to plain language plus a technical `detail` kept for the "Technical details" expander. A manifest that arrives but cannot be decoded is reported as a server problem, not "check your internet".

## Keys
- One keypair, generated with `tauri signer generate`. The **public** key is committed. The **private key and its password are secrets**: they live only in GitHub Actions secrets (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`) and in the owner's own backup. `*.key` is in `.gitignore`.
- **Backups:** a protected read-only copy lives in `C:\ProgramData\BetterClaudeUI\updater-key-backup\` and `node tools/check-updater-key.mjs` verifies it (see `docs/RELEASING.md`). The key is the *project's* publishing key; end users never hold it and installed apps only contain the public half, so app corruption or a reinstall cannot affect update ability.
- **Losing the private key means installed copies can never be updated** (they would have to be reinstalled by hand with a build containing a new public key). Rotating keys is therefore a breaking operation; back the key up.
- This is separate from OS code signing (Windows Authenticode, macOS notarization), which is not done.

## How it was verified
- Unit tests: error classification, HTTPS rule, notes trimming, endpoint parsing (Rust); scheduling and the update state machine (TypeScript).
- Real app (debug build) against `tools/update-server.mjs`, which signs a payload with the real key: genuine update found, downloaded and **verified**; tampered bytes and a payload signed with a different key are **rejected**; malformed manifest, 404 and offline give friendly messages and leave the app working (`node tools/e2e.mjs updater`). The test stops at "Install and restart" and never clicks it.
- A locally signed release build's real installer and `.sig` verify against the app's public key (`BCU_REAL_ARTIFACT`).

- **Real install and relaunch on Windows (2026-11-26, owner-approved):** a test 0.1.0 was installed silently, updated through the real UI to a signed 0.1.1 served from a local HTTPS test server, and relaunched on 0.1.1 within about 8 s (`tools/update-install-test.mjs`), then fully uninstalled.
- A genuine installer signed for an OLDER version but announced as newer is rejected by the plugin's signed-version check (replay protection), and a plain-HTTP download is refused in release builds.

## Not verified / limits
- macOS and Linux update paths have never been run on real hardware.
- `latest.json` is generated by `tauri-action` in CI and only becomes reachable at the `latest/download` URL once a release is published (a draft is not public).
